# 対話ポイント定義（CP-1〜CP-8）— KATHERINE 対話型レポート作成モード

> 本ファイルは `interactive/SKILL_INTERACTIVE.md` §5 が参照する、8 つの対話ポイント（CP）の
> 実施定義の正本。**進行の正本は `capcom_schema/SKILL.md` の Phase A〜D**（各 STOP-GATE・
> 保存形式・完了条件・数値基準はすべて SKILL.md と `analysis/` 正本に従い、本ファイルには複製しない）。
> 各 CP は SKILL.md の該当ステップに「提示 → 対話 → 確定」を重ねる差分定義である。

---

## 提示テンプレート（全 CP 共通・4 部構成）

AI の提案は必ず次の 4 部で提示する（SKILL_INTERACTIVE.md §0-I I-1。順序も固定）:

| 部 | 内容 | 書き方 |
|---|---|---|
| **【提案】** | 判断案・選択肢 | 原則 2〜3 案。推奨案に「（推奨）」を付す。1 案しか立たない場合は 1 案でよい |
| **【根拠】** | 使ったデータと数値・適用した基準・判断の手順 | 「どの数値を見て → どの基準に当てて → どう判断したか」の順で簡潔に。基準は読者向け呼称で言及（例: 「母集団タイプの判定基準では上位N社シェアが◯◯%を超える場合…」） |
| **【別の見方】** | 検討したが採らなかった解釈と、採らなかった理由 | 1〜2 個。**本気で成立しうる解釈のみ**（最初から負けるように作った形だけの別解釈＝藁人形は禁止）。該当なしなら本部ごと省略可 |
| **【確認したいこと】** | 分析者に確定してほしい事項 | `AskUserQuestion` の選択肢と 1 対 1 で対応させる |

**共通ルール**:
1. 提示・対話の中でも内部ファイル名・内部フィールド名・内部ガイドファイル名を出さない
   （`analysis/terminology.md` の正式呼称を使う。レポート本文と同じ規律を会話にも適用）。
2. 根拠は要点主義。数値と基準の引用にとどめ、長い講釈をしない（1 CP の提示は目安 30 行以内。
   ただしルール 5 のマップの見方の説明はこの目安の外とし、省略しない）。
3. 自由記述・修正指示はチャットで受け、確定はツールで取る。長文は `reports/_analyst_notes.md` 経由でもよい。
4. 分析者が自分の仮説・解釈を出してきたら誠実にレビューする（データ・基準と矛盾すれば
   根拠を添えて指摘する = I-3）。
5. **マップ・可視化を根拠に使う場合は、最初にそのマップの見方（点・線・色・軸・距離が何を
   表すか）を 1〜2 行添える**。そのマップに馴染みのない分析者でも提示のロジックを追える状態を
   作るのが目的（CP-4 に限らず、CP-6 の検証結果や CP-7 の事実サマリでマップに言及するときも
   同様。見方・注意点の正本: `analysis/map_reading.md` の該当マップ種別の節）。

## 確定の選択肢設計（共通規則・AskUserQuestion の 4 択制約対応）

基本形は次の 4 択（CP ごとに文言を具体化してよいが、**「🤖 おまかせ」は必ず含める**）:

1. **✅ この案で確定**（推奨案をそのまま採用）
2. **✏️ 修正して確定**（修正内容はチャットで受ける → 反映した確定値を 1 行で復唱して確定）
3. **🔄 別案・差し替え**（分析者の案や別方向をチャットで受ける → 4 部構成で再提示 → 再確定）
4. **🤖 おまかせ**（この項目は自律生成モードと同じ判断で進行。判断ログに `[対話→委任]` と記録）

- 既存 STOP-GATE に CP を重ねる場合（CP-1/2/3/5）は、**SKILL.md 側で定義された選択肢を優先**し、
  そこに「🤖 おまかせ」の趣旨が含まれない場合のみ Other 誘導または文言統合で補う
  （SKILL.md の選択肢仕様を崩さない。例: STOP-GATE C の 5 択はそのまま使う）。
- **委任（おまかせ）の粒度**: 「🤖 おまかせ」の既定スコープは**その確定 1 件分**（CP-7 なら
  当該モジュール 1 章分）。複数章・フェーズ全体の一括委任は、選択肢にその旨を明示して
  分析者が選んだ場合のみ成立する（判断ログに「全章委任」等とスコープを明記）。
- **抱き合わせ禁止**: 既存 STOP-GATE の確認（例: Phase C 計画確認）と、CP の進め方・委任の
  確認を **1 つの質問にまとめない**。必ず別々の質問として確定を取る（まとめると「計画を
  承認したつもりが全対話を委任していた」事故が起きる）。
- 再確定のループは 1 CP につき原則 2 回まで。収束しない場合は論点を判断ログに記録し、
  分析者に「現時点の案で仮確定して先へ進み、Phase D の結論確定（CP-8）で再訪する」ことを提案する。


## CP-1 検索式の読解 — Phase A STOP-GATE A に重ねる

- **発動条件**: `population_meta.query_logic` 指定時のみ（未指定時のスキップ規則は SKILL.md と同一）。
- **提示**:
  - 【提案】検索式の構造化読解（ブロック分解・各条件の意図推定）を採用案として提示
  - 【根拠】各ブロックの構文と「この式が**採るもの・落とすもの**」の具体例、使用データベースの
    構文規則（該当があれば固有の注意点も。例: スペースが暗黙 OR になる DB）
  - 【別の見方】解釈の幅がある条件（例: ある分類記号を含むか曖昧な語）の別読みとその影響
  - 【確認したいこと】この読解で進めてよいか・危うい箇所への対処
- **確定**: SKILL.md STOP-GATE A の選択肢（✅ この読解で進める / ✏️ 誤りがある / 💬 補足追加）を
  そのまま使う。意図↔論理の乖離が見つかった場合の対処も SKILL.md STOP-GATE B の
  A/B/C 選択のまま（提示に改善提案の根拠を添える）。
- **おまかせ時**: SKILL.md STOP-GATE A/B の標準進行（確認自体は必須ゲートなので省略不可。
  委任されるのは「読解の対話的深掘り」の部分）。

## CP-2 母集団タイプの判定 — Phase A STOP-GATE C に重ねる 【ライトでも実施】

- **提示**（ワンショット統計スクリプトの 1 回実行後）:
  - 【提案】母集団タイプ（A/A'/B/C/D）の判定案と、分析の立場（narrative_stance）の推定案
  - 【根拠】上位N社シェア・年次分布・主要分類などの実数値 → 判定基準（シェア閾値のマトリクス）の
    どの行に該当したか → 設計意図・検索式との裏付け。**このタイプで禁止される表現とその理由**
    （例: 単一企業母集団で出願人集中度を語っても意味がない）も必ず添える
  - 【別の見方】判定が際どい場合の次点タイプと、それを採らなかった決め手
  - 【確認したいこと】タイプ・立場・偏り警告への対処
- **確定**: SKILL.md STOP-GATE C-3 の統合確認（5 択）と、関係性立場の場合の自社名確認を
  そのまま使う。確定値の保存形式（`_phase_a_decisions.json`）も SKILL.md のまま。
- **おまかせ時**: STOP-GATE C 自体は必須ゲートなので実施する（委任されるのは根拠の対話的深掘り）。

## CP-3 サブクエスチョン — Phase A サブクエスチョン化 STOP-GATE に重ねる

- **発動条件**: `query_intent` 指定時のみ（スキップ規則は SKILL.md と同一）。
- **提示**:
  - 【提案】本分析が明らかにすべき具体的観点（サブクエスチョン）の案
    （個数は SKILL.md サブクエスチョン化 STOP-GATE の規定に従う）
  - 【根拠】各観点について「設計意図・Mission Objective のどこから導いたか」
    「手元のデータで答えられる根拠（使うデータと数値の当たり）」
  - 【別の見方】検討したが外した観点と外した理由（例: データで検証できない・範囲外）
  - 【確認したいこと】この分解で進めてよいか・追加/削除
- **確定**: SKILL.md の選択肢（✅ / ✏️ / 💬）のまま。分析者の追加案は歓迎し、
  「データで答えられるか」の観点でレビューして取り込む。
- **おまかせ時**: SKILL.md の標準進行。

## CP-4 マップ読解 — Phase B Evidence 精読に重ねる

- **対象**: 主要マップ 2〜3 枚（俯瞰図・クラスタ動態マップなど、Mission Objective に効くもの。
  枚数を絞るのはコンテキスト規律のため。全マップの分析・掲載義務は SKILL.md / gate の基準のまま）。
- **提示**（1 枚ごと。**読解のロジックを次の 4 点構成で全て開示する** — マップに馴染みのない
  分析者が、AI と同じ手順で同じ読みに到達できることを目指す）:
  - 【提案】このマップから採用する観察（読み取り）の案
  - 【根拠】次の順で読解の過程を開示する:
    1. **マップの見方** — 点・線・色・軸・距離が何を表すか（1〜2 行。例: 俯瞰図なら
       「1 点 = 1 件の特許、点同士の近さ = 内容の類似、色 = クラスタ。**点間距離は相対的な
       近さであり、絶対値に意味はない**」、共起ネットワークなら「ノード = キーワード、
       線 = 同じ特許の中で一緒に使われた関係、線の太さ = 共起の強さ、中心にある語 =
       多くの語をつなぐ結節点」）
    2. **読解の手順** — 何に着目し → どのデータ・数値で確かめ → 何を読み取ったか
       （マップ読解の正本ガイドにある当該マップ種別の読解手順〈5 ステップ〉に沿って開示）
    3. **裏づけの数値** — クラスタ件数・共起の強さ・中心性・年次分布など、読み取りを支える実数値
    4. **誤読しやすい点・このマップから言えないこと** — 正本ガイドが挙げる当該マップ種別の
       注意点を該当分だけ示す（例: 共起の線の太さは「重要度」ではない／俯瞰図のクラスタ間
       距離を定量的な技術距離として読まない／あるはずなのに無い語・空白領域にも意味がある）
  - 【別の見方】同じマップの別解釈（例: 密集を「技術的近接」でなく「データの偏り」と読む可能性）
    と、採らなかった理由
  - 【確認したいこと】採用する観察の確認・追加で見たい観点
- **確定**: 基本 4 択。1 枚につき確定ラウンドは原則 1 回（コンテキスト規律）。
- **おまかせ時 / ライト時**: 自律進行（読解結果は Evidence 精読メモとして通常どおり作成）。

## CP-5 クロスパターン選択 — Phase B STOP-GATE 1 に重ねる

- **提示**:
  - 【提案】採用するクロス分析パターンの推奨セット（**SKILL.md Phase B 完了条件に定める
    クロス分析パターンの最低数**以上）＋次点 2〜3
  - 【根拠】各パターンについて「Mission Objective・サブクエスチョンとの適合理由 /
    検証に使うデータ / 期待される発見」を 1 行ずつ
  - 【別の見方】外したパターンとその理由（例: 必要なデータが未実行モジュールのもの）
  - 【確認したいこと】このセットで進めるか・入れ替え/追加
- **確定**: SKILL.md STOP-GATE 1 の確認をそのまま使う（選定数の下限は非交渉 = §0-I I-3。
  下限は SKILL.md **Phase B 完了条件**のもの。STOP-GATE 1 の読了確認に書かれた選定数ではない）。
- **おまかせ時 / ライト時**: SKILL.md の標準進行。

## CP-6 仮説と検証 — Phase B クロス分析実行に重ねる 【ライトでも実施（仮説確認のみ）】

パターンごとに次の 2 段で対話する。**往復を抑えるため、パターン 2〜3 個をまとめて 1 回の
提示・確定にバッチしてよい**（1 パターンずつ 8 往復するのは避ける）。

**第 1 段（検証前・仮説の確認）**:
- 【提案】各パターンの仮説案（1 文。「X だから Y のはずだ」の形）
- 【根拠】なぜこの仮説を立てるか（先行する観察・データの示唆・設計意図との関係）
- 【別の見方】同じパターンで立ちうる別仮説
- 【確認したいこと】この仮説で検証してよいか（分析者の自前仮説も歓迎）

**第 2 段（検証後・判定の確定）**:
- 【提案】検証結果に基づく判定案（支持 / 棄却 / 条件付き支持）と結論文の案
- 【根拠】検証で得た実数値を仮説と対比して提示。**棄却された場合は「なぜ外れたか」の解釈を
  特に丁寧に開示する**（想定と違う結果こそ発見の種）
- 【別の見方】同じ数値の別解釈（成立しうるもののみ）
- 【確認したいこと】判定と結論文の確定
- **確定**: 基本 4 択（バッチ時は「一括確定 / 個別に見る」を選択肢に含めてよい）。
- **ライト時**: 第 1 段のみ対話し、第 2 段は自律で進めて結果サマリを提示する
  （判定に異論があれば分析者はいつでも差し戻せる）。
- **おまかせ時**: SKILL.md の標準進行（仮説→検証→結論の記録義務は同一）。

## CP-7 統合インサイト — Phase C 各 deep_dive に重ねる

モジュールごとに、deep_dive の**統合インサイト節（章の主張・示唆・提言の種）を書く前**に対話する。
本文の執筆・書式・内容量の担保は従来どおり AI の責任（分析者入力が品質ゲート不合格を招く
経路を作らない）。

- **提示**:
  - 【提案】この章の統合インサイト案（要点・示唆・提言の種を箇条書き 3〜5 行）
  - 【根拠】次の 2 点を必ず含める:
    1. **データ突合の開示** — この章で組み合わせたデータを「**特許×特許**」「**特許×NPL**」
       「**NPL×NPL**」の別で明示し（例: クラスタ構成〈特許〉× 動態マップ〈特許〉、
       特許クラスタ × 学術クラスタ〈NPL〉、学術トレンド × ニュース・政策〈NPL〉）、
       **突き合わせた結果の一致点と矛盾点を各 1 行以上**書く。矛盾・食い違いは隠さず提示する
       （想定と合わない突合結果こそ発見の種）。該当する組み合わせが無い場合は「なし」と明示する
    2. **支える数値** — そのモジュールのデータ・AI インサイト・クロス分析結果からの実数値と、
       どのサブクエスチョンに答える内容か
  - 【別の見方】対立しうる解釈と、それを採らなかった決め手（この対話が本文の
    「結論の検証（別解釈＋決め手）」の素材になる）
  - 【確認したいこと】この方向で本文を書いてよいか
- **確定**: 基本 4 択。確定後に AI が本文を執筆し、分析者は通読して違和感を指摘できる
  （修正は AI が行う）。**Phase C 計画確認（既存 STOP-GATE）と CP-7 の進め方確認は別質問**
  （§共通規則の抱き合わせ禁止）。
- **代表特許の扱い**: 決定的選定の仕組み（なぜ AI の自由選択にしないか＝つまみ食い防止）を
  最初のモジュールで 1 回説明する。分析者が興味を持った特許の照会は自由分析として受けるが、
  **本文の引用は選定リスト記載の番号のみ**（SKILL.md / gate の基準のまま）と明示する。
- **ライト時**: 自律進行。ただし分析者が希望すれば 2〜3 モジュールに限定して実施してよい。
- **おまかせ時**: SKILL.md の標準進行。ただし**委任の既定単位は当該モジュール 1 章分**
  （全章一括の委任は §共通規則の粒度ルールに従い、明示の選択でのみ成立）。**全章委任が成立した
  場合・ライト深度で自律進行する場合でも、各モジュール完了ごとに「突合サマリ」（使用データ・
  突合の組み合わせ〈特許×特許／特許×NPL／NPL×NPL〉・一致点/矛盾点を 3〜5 行）を提示する**。
  応答は求めない（過程の透明化は委任中も維持する。ここが不透明になると本モードの存在理由が
  失われる）。

## CP-8 結論の確定 + WARN トリアージ — Phase D に重ねる 【ライトでも実施】

**(a) 結論の確定（結論章の執筆前）**:
- 【提案】主要結論の案 2〜3 個と、それぞれに対応する提言の骨子（確定済みの分析の立場に
  沿った型で）
- 【根拠】結論ごとに「支える数値・特許・Web 裏付け」→「**別解釈との比較**（成立しうる別解釈・
  それを退けた決め手・残る不確実性）」→「**この結論の前提と、崩れる場合に最初に観測される
  サイン**」まで提示する（レポート必須要素である結論の検証・見直しのサインを、対話の中で
  分析者と確定する運用。書式・掲載義務は SKILL.md / gate の基準のまま）
- 【別の見方】採用しなかった結論候補（データが弱い・別解釈を退けきれない等の理由つき)
- 【確認したいこと】各結論の採否・修正・提言骨子の調整
- **確定**: 結論ごとに採否を取る（基本 4 択をまとめて適用してよい）。**最終 GO/NO-GO は分析者**。
  確定後、AI が結論章と `report.typ` 統合を執筆する（構成確認 STOP-GATE は SKILL.md のまま）。

**(b) WARN トリアージ（`phase_d_gate.sh` 実行後）**:
- FAIL は従来どおり AI 主導の強制修正ループ（分析者の同意でも緩和不可）。
- **WARN は 1 件ずつ**「該当箇所の本文抜粋 + なぜ警告されたか + 直す場合の案 / 残してよい場合の
  考え方」を提示し、**分析者が直す / 残すを判断**する。判断と理由を判断ログに記録する
  （機械ゲートは注意の誘導であり、意味の最終判断は人間、という既存の運用を対話で実施するもの）。
- WARN が多数の場合は種類ごとにまとめて提示してよい（1 件ずつの判断記録は維持）。
- **ライト時**: (a)(b) とも実施する（本 CP は対話型の最低限の中核）。
- **おまかせ時**: (a) は自律判断で結論を確定（判断ログに委任記録）。(b) の WARN 判断も
  委任可能だが、その場合「WARN を AI 判断で処理した」旨を最終報告に明記する。
