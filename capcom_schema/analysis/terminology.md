> このファイルは `SKILL.md` 配下の最優先ガイドラインです。

## 0. 最重要原則

**レポート受容者（人間の読者）は APOLLO（分析プラットフォーム）の内部構造を知りません。** 読者にとって `spatial_context`, `cluster_dynamics`, `saturnv_clusters.json`, `data_notes.md`, `quadrant_summary` といった内部識別子は意味不明な英単語に過ぎず、レポートの可読性と信頼性を毀損します。旧 APOLLO 時代のモジュールコードネーム（Saturn V・ATLAS・MEGA 等）も同様に内部識別子であり、本文では §2-B / §2-C の機能名に読み替えます。

**この用語表は、内部識別子が外部向けレポートに漏出することを防ぎ、どのツール（Claude Code / Codex / Antigravity）でレポートを生成しても同じ呼称が使われることを保証するために存在します。**

## 4. Mission Objective の扱い — 絶対遵守

**共通規律: ユーザー入力の原文（`mission_objective` と `query_intent` §5-A）は、レポートのどこにもベタ貼りしてはいけない。執筆者が咀嚼して自然な日本語で書き下す。** `voyager/mission.json` の `mission_objective` にはユーザーが入力した**分析の問い**の原文が格納されているが、どの章（エグゼクティブサマリー・本分析の問いと回答・クロスモジュール統合分析等）でもそのまま転記せず（語尾だけ削った貼付けも不可）、「本分析が答えようとしている問い」を**自然な日本語 1-2 行**として書き下す。原文の語順・箇条書き構造・会話的な語尾（「〜してください」等）・固有名詞の使い方をコピーしないこと。

ユーザー入力 `mission_objective`: 「A 社の次の商品開発と、必要であれば M&A 候補の分析を行ってください」
> ❌ **NG（原文ベタ貼り）**: `本レポートは『A 社の次の商品開発と、必要であれば M&A 候補の分析を行ってください』という問いに対し、...`
> ✅ **OK（咀嚼して書き下し）**: `本レポートは、A 社が次に投入すべき商品領域と、それを実現するための外部連携（M&A を含む提携候補）を特定することを目的としている。`

**各章での適用**: ①エグゼクティブサマリー冒頭 — 咀嚼した問い 1-2 行 + 直接回答 3-5 行（原文引用禁止）／②本編「本分析の前提」章 — `query_intent` の設計意図と合わせて咀嚼／③クロスモジュール統合分析・結論章 — 咀嚼した 1 行で参照（「Mission Objective『...』によれば」のような引用禁止）／④別冊（経営層向け要約版） — 本編と同じ咀嚼文を使う（本編と別冊で咀嚼文が食い違うのは品質不合格）。

**咀嚼のガイドライン**: 原文から**分析対象（企業・技術領域）・目的（何を明らかにするか）・制約/除外条件**の 3 要素を抽出し、「〜を目的としている」等の**宣言調・論述調**で再構成する。会話的表現（「〜してください」「〜してほしい」）は排除し、「必要であれば」等の曖昧な条件はそのまま転記せず**分析の観点として書き下す**。

### 5-A. `query_intent` の取り扱い — 絶対遵守の 3 原則

**原則 1: ベタ貼り禁止（§4 と共通規律）**
- `query_intent` の原文をどこにも転記しない（本分析の前提章・付録 D・各 deep_dive すべて）。「本分析の前提」章では 3〜5 行の自然な日本語段落として**書き下す**（構成要素: ①分析目的、②母集団の輪郭＝何を含め何を除外したか、③どの切り口を重視するか）。用語・語順・箇条書き構造を原文から流用せず、Mission Objective とも結び付けた「本分析を読むための視座」として提示する

**原則 2: ユーザーとの対話で設計理解を確定させる（STOP-GATE）**
- Phase A で `query_intent` を読み取った段階で、執筆者は自分の言葉で「分析目的・母集団の輪郭・視座」の 3 点を整理し、`AskUserQuestion` ツールで**ユーザーに確認する**
- ユーザーが「この理解で進める / 修正が必要 / 補足を追加」を返すまで次のステップに進めない
- 確定したあとで初めて、その理解を本分析の視座として作業メモに固定する
- AI 側が自動で解釈を確定して進めるのは禁止（設計意図の解釈は分析の根幹に関わるため、必ずユーザー合意を経由する）
- `query_intent` が未指定の場合はこの対話ゲートを省略してよい（その旨をユーザーに 1 行で報告）

**原則 3: 全分析を通じた視座として機能させる**
- Phase B の Evidence 精読・クロスモジュール分析・Phase C の各 deep_dive・Phase D の結論章すべてで、確定した視座を分析の視座として内在化させる
- **指定章で明示的な意図参照を義務化**（下記 5-A-1）: エグゼクティブサマリー冒頭 / 各 deep_dive 冒頭 / クロスモジュール分析の結論段 / 戦略的提言 / 仮説検証サマリー
- 意図に沿った論点を優先的に掘り下げる
- 意図と整合しない結果（除外したはずの領域が部分的に混入している等）は、本文に分散させずに **Phase D で独立した章「分析過程で確認された追加的事項」** にまとめる（`analysis/report_structure.md` §7 参照）
- 設計意図を無視した汎用的な分析は品質不合格

### 5-A-1. 指定章での意図参照の義務化（強度「中」）

以下 5 つの章では、**「本分析の視座」「設計意図に照らすと」「当初の分析観点では」等の参照表現を最低 1 箇所**含めること。検出は Phase D gate `Check 12` で自動実施（本文内の意図参照語をカウント）:

| 章 | 義務化される意図参照の例 |
|---|---|
| **エグゼクティブサマリー冒頭** | 「本分析の視座（〜）に即して答えると、〜が明らかとなった」（宣言調、問い形式禁止） |
| **各 deep_dive 冒頭** | 「本章は {視座} の観点から、〜を読み解くものである」 |
| **クロスモジュール分析の結論段** | 「本分析の視座に照らすと、この結果は〜を示唆している」 |
| **戦略的提言** | 「本分析の視座から導出される提言として、〜」 |
| **仮説検証サマリー** | 「各仮説は、本分析の視座との整合性の観点で検証された」 |

### 5-A-2. サブクエスチョン化（Phase A で執筆者の作業メモ用として作成）

Phase A の `query_intent` 3 点整理（分析目的・母集団の輪郭・視座）を、**さらに具体的な分析観点 3-5 個に分解**し、`reports/_phase_a_decisions.json` の `sub_questions` フィールドに保存する。

**重要制約（絶対遵守）**: サブクエスチョンは**執筆者（エージェント）の作業メモ専用**。レポート本文には「問い / 答え」「Q1 / A1」等の形式で書いてはいけない（本文は通常の**宣言調の論述**）。「Q1: 最大の成長領域はどこか？」のような問い文・「A1: X 技術ポケットである」のような回答文・「本分析の問い『…』に対しては」のような問いへの直接言及は品質不合格。

**役割**: ①Phase B/C/D で「何を明らかにすべきか」を見失わないための内部指針 ②Phase D 結論章で意図由来の論点が漏れなくカバーされたかの自己点検 ③Phase D gate `Check 12` でサブクエスチョンの**キーワード**が本文に登場するかを自動検証。

**Phase A での作成手順**: 3 点整理をユーザーと合意 → 「明らかにすべき具体的観点」3-5 個を箇条書きで起草（問い形式で起草してよい。レポート本文ではない）→ **確定した立場（narrative_stance §6-2-B）の観点で SQ の抜けを点検**（self=自社の弱点・空白／competitor=対象企業の隙・参入余地／neutral=強み・リスク・投資妙味。ただし query_intent を最優先＝機械的置換でなく抜けの点検）→ 各 SQ から主要キーワード 1-3 個を抽出 → `AskUserQuestion` で一覧+キーワードを提示し「進める / 修正 / 追加」をユーザーが選択 → 確定結果を `sub_questions` に保存。

**保存形式（最小例）**:
```json
{"sub_questions": [
  {"id": "SQ1", "content": "本母集団で最も成長している技術領域はどこか", "keywords": ["成長", "技術領域"]}
]}
```

❌ **NG（問い / 答え形式）**:
> **Q1: 最大成長領域はどこか?** A1: 本母集団ではタイヤ用ゴム複合材料領域が CAGR +254% で最大成長している。

✅ **OK（宣言調の通常論述、意図参照あり）**:
> 本分析の視座である「自社の注力領域選定」に即して成長動向を精査すると、タイヤ用ゴム複合材料領域が CAGR +254% と本母集団内で群を抜いて伸長している。一方で自社の出願はこの領域に集中しておらず、重要な空白領域として位置づけられる。

**いずれも空文字（未指定）の場合**は、以下のフォールバック表記を使用：
- `query_intent` 未指定 → 「本分析の前提」章の「分析の視座」サブセクションごと省略。全 deep_dive での「視座に照らした解釈」も省略してよい
- `query_logic` 未指定 → 付録 D ごと省略（「非公開」等と書かない）
- `coverage_years` 未指定 → `context.json` の `dataset.period`（出願年の最小〜最大から自動算出）を使用
- `database_name` 未指定 → 「提供された特許データセット」と一般化表記

### 5-B. `query_logic`（母集団検索式）の構造化読解 — Phase A STOP-GATE A

`query_logic` 指定時は付録 D へのコピペだけでなく、Phase A で 3 つの STOP-GATE を経由する（必須手続き・省略不能。`SKILL.md ## 0. 絶対遵守ゲートルール` 第 1-2 項）。正本は `analysis/query_logic_reading.md`:
- **STOP-GATE A（構造化読解）**: DB 識別 → 構文分解 → 意図推定 → `AskUserQuestion` でユーザー確認（4 ステップ詳細: 同 §1）
- **STOP-GATE B（意図↔論理 整合性検査）**: `query_intent`・`query_logic` 両方指定時、8 項目チェックリスト（同 §4）で乖離を Critical/Warning/Info に分類し、改善提案を添えてユーザー確認
- **STOP-GATE C（データ側からの逆読み）**: 全ケースで実施。patents.csv の実態（出願人/IPC/年分布/HHI 等）と設計意図・検索式の整合を確認（統合フロー: 同 §6）

## 6. スコープ限定ルール — 「本母集団」と「業界全体」を混同させない（絶対遵守）

> **関連**: 本節は全タイプ共通の基本防壁。**母集団タイプ（A/A'/B/C/D）ごとに追加の表現禁止ルール**が `analysis/population_type_metrics.md` §3 にある。両者を併せて適用すること。
> - 本 §6: 全タイプで「本母集団では〜」等の限定修飾を必須化
> - `population_type_metrics.md` §3: タイプ B/C/D で「市場集中」「業界シェア」等の特定表現を追加禁止

### 6-0. なぜこのルールがあるのか

APOLLO の分析対象は常に **ユーザーが検索式で絞り込んだ特許母集団** であり、**業界全体・市場全体・技術分野全体** ではない。読者は検索式を暗記していないため、主語を曖昧にすると「本母集団の中では A 社が 1 位」を「業界で A 社が 1 位」と読むような誤解が生じ、経営判断を致命的に誤らせる（特に別冊）。本節は「どこまでが母集団内の観察か／どこからが母集団外への一般化か」を読者が瞬時に判別できるようにするための構造的防壁である。

### 6-1. 禁止表現（修飾なしの主語無限化）

**原則: 母集団外を主語にした無限化表現を、「本母集団では／本分析では／本対象特許群では」等の限定修飾なしに使うのは品質不合格**。対象:

- 「業界では／業界全体では」「市場では／市場全体で」「産業では／当該産業では」（業界・市場・産業 ≠ 本母集団。市場は特許ではなく売上・シェア）
- 「業界の標準／主流／トレンド」（本母集団の観察は業界標準を直接示さない）
- 「全体として〜」の単独使用（何の全体か不明。「本母集団全体として」等に限定）
- 「技術分野では／この技術領域では」（別の検索式なら別の結果）
- 「企業の間では／各社は」「主要プレイヤーは」の無限化（「本母集団の主要出願人は〜」等、本母集団に含まれる出願人に限定）
- 「日本では／グローバルでは」等の地理的一般化（データベースが地域限定なら不可）

### 6-2. 必須表現（母集団限定を明示する修飾）

無限化表現の代わりに、以下のいずれかの限定修飾を必ず文頭・文中に含める: 「本母集団では」（万能）／「本分析の特許群では」「本対象特許群では」／「本検索式で抽出された範囲では」／「本データセット内では」／「{database_name}（{coverage_years}）の範囲では」／「本分析の対象（{total_patents} 件）では」／出願人ランキングでは「本母集団に含まれる出願人では」「本母集団の上位 N 社では」。

### 6-2-A. 🚫 国籍・地域のトートロジー（循環論法）の絶対禁止 — 最頻の致命的誤読

母集団が**国・地域・言語で絞られている**場合（例: 日本特許庁の日本語公報＝日本出願）、その国・地域が「多い／主導する／牽引する／世界をリードする」と結論づけるのは**循環論法（トートロジー）であり品質不合格**。母集団の定義上その国の出願が多く海外勢が少ないのは当然の帰結で、技術的優位・成長主導の根拠には一切ならない。**限定修飾（「本母集団では」）を付けても解消しない**（同義反復のまま、読者・特に経営層に「日本が世界で主導」という誤った含意を与える）。

| ❌ 禁止（国籍トートロジー） | ✅ 正しい書き方 |
|---|---|
| 「日本企業が成長を主導している」 | 「本母集団は日本語公報に限定されるため、海外勢の出願動向は本分析の評価対象外である。出願人間の比較は国籍ではなく企業単位で行う」 |
| 「海外勢は衰退ニッチに偏り、日本が牽引している」 | 「海外勢の日本語公報への出願は限定的であり、これは各社のグローバルな出願動向ではなく日本市場向け出願の有無を反映しているに過ぎない」 |
| 「日本が世界をリードする技術領域」 | 「本母集団（日本出願）で出願が厚い技術領域。世界全体での日本の地位は、外部データ（#footnote）なしには判断できない」 |

**判定基準**: 母集団国（日本等）を主語に「牽引／主導／リード／世界を」を述語にする文は、たとえ留保文を併記していても削除または上記の置換を行うこと。**国別の優劣・主導は、Web 調査の外部統計（出願の国際比較・市場シェア等）を `#footnote` で引用した場合にのみ論じてよい**（その場合も「本母集団の観察」ではなく「外部データの引用」として明確に分離する）。

> 注: 「グローバル学術研究は活発だが本母集団（日本特許）では薄い」のような**逆向きの非対称比較**（自国が"薄い"ことの指摘）は、ホワイトスペース論として妥当であり本ルールに抵触しない。禁止されるのは「自国が"主導/牽引"している」という**優位の主張**である。

### 6-2-B. 🎯 分析の立場（誰の意思決定のための分析か）— 「当社」を勝手に使わない

レポートの提言・主張は、**誰の意思決定のために書くか（＝分析の立場）** を Phase A STOP-GATE C で確定し、全章で一貫させる。母集団が単一企業（タイプ C）でも、**読者＝依頼主は対象企業自身とは限らない**（競合・投資家・アナリストが対象企業を分析することも多い）。立場は `_phase_a_decisions.json` の `narrative_stance.code` に記録される。

| 立場（code） | 対象企業の呼称 | 一人称「当社/弊社/我が社」 | 提言の方向 |
|---|---|---|---|
| **self**（自社視点） | 「当社」 | 可 | 自社の打ち手 |
| **competitor**（競合視点／水平） | 企業名・「同社」で三人称 | 読み手＝競合自身を指す時のみ | 対象企業への対抗・差別化・参入 |
| **buyer**（**自社＝買い手／対象＝供給元**。自社が対象から仕入れる側） | 企業名・「同社」で三人称 | 読み手＝買い手自身を指す時のみ | 調達戦略・依存/供給途絶リスク・共同開発の是非・代替調達 |
| **supplier**（**自社＝供給元／対象＝顧客**。自社が対象に納入する側） | 企業名・「同社」で三人称 | 読み手＝供給側自身を指す時のみ | 供給深耕・内製化(自社外し)リスク・先回り開発・スイッチング防止 |
| **neutral**（中立／投資家・アナリスト） | 企業名・「同社」で三人称 | **不可** | 中立的な評価・示唆 |

> 🧭 **コードは常に「自社の役割」を表す（対象＝相手方）**: `competitor`＝自社が競合／`buyer`＝**自社が買い手**（対象＝供給元）／`supplier`＝**自社が供給元**（対象＝顧客）。**「buyer＝対象が買い手」ではない**（混同すると分析の向きが逆転する）。判別法は「**モノ／カネの流れ**」——自社が対象から**仕入れる**なら `buyer`、対象に**売る**なら `supplier`。例（対象＝キオクシア）: 自社＝Apple（NAND を買う）は **buyer**／自社＝東京エレクトロン（装置を売る）は **supplier**。

**絶対ルール**:
- `narrative_stance.code` が `self` **以外**のとき、対象企業を「当社」「弊社」「我が社」と呼んではならない（必ず企業名または「同社」で三人称）。
- 立場が `neutral` のとき、提言は「○○社は〜すべき」「〜と評価できる」と第三者の評価形にする。「当社は〜する」と当事者化しない。
- 一つのレポート内で「当社」と「同社／企業名」を混在させない。
- **`competitor` / `buyer` / `supplier` は「関係性立場」**（自社 ≠ 対象で、対象を三人称に置く）。3 つとも分析を行う**自社**（`own_company`）を持ち、Web 調査で自社を調べて対象企業と対比する（下記「関係性立場では〜」）。水平か垂直かが違うだけで、呼称ルール（三人称・「当社」は読み手＝自社自身の時のみ可）は共通。

| ❌ NG（立場 neutral なのに当事者化） | ✅ OK（中立の三人称） |
|---|---|
| 「当社は製造投資を継続すべきである」 | 「キオクシアは製造投資を継続すると見られ、この方針は妥当と評価できる」 |

#### 立場は呼称だけでなく「分析の力点・解釈・提言のロジック」を規定する（最重要）

立場を変える ＝ 「当社」を企業名に置換するだけ、ではない。**同じ事実でも、立場によって読み方（Layer 3 洞察）と打ち手（Layer 4 提言）が変わる**。呼称だけ三人称にして中身が `self` の「べき論」のままにしてはならない。

| 観点 | **self**（自社視点） | **competitor**（競合視点） | **neutral**（中立／投資家・アナリスト） |
|---|---|---|---|
| Layer 3 洞察の力点 | 自社の強み/弱み/空白の**内省** | 対象企業の隙・牙城を**機会／脅威**として読む | 客観的な**強弱・リスクの評価** |
| Layer 4 提言の型 | 自社が取る**打ち手**（投資/出願強化/撤退）。実行可能性を重視 | 競合としての**対抗・差別化・参入**。相手の出方を読む | **評価・予測**（自らは実行主体でない）。投資/提携/M&A の判断材料 |
| 提言の述語 | 「当社は〜すべき／〜する」 | 「（競合として）対象企業が手薄な X で先行する余地がある」 | 「〜と見られる／〜が評価ポイント／〜と評価できる」 |

**同じ事実が立場で変わる例**（事実＝「メモリシステム領域の出願が薄い」）:
- `neutral` ✅「キオクシアはメモリシステム領域の出願が限定的で、NAND 依存からの脱却は道半ば。AI 需要を取り込めるかが中期の評価ポイントとなる」（リスク → 評価）
- ❌ 悪い例（`neutral` なのに `self` の中身を三人称化しただけ）「キオクシアはメモリシステム領域の出願を強化すべきである」← 当事者の「べき論」を三人称にしただけで、第三者の評価になっていない

**関係性立場の垂直版（buyer / supplier）の力点**（competitor と同じ「自社 ≠ 対象」だが、読む方向が縦になる）:

| 観点 | **buyer**（取引先／買い手・下流） | **supplier**（サプライヤー・上流） |
|---|---|---|
| Layer 3 洞察の力点 | 対象（供給元候補）の技術ロードマップ・依存リスク・**供給側の集中度** | 対象（顧客）の技術投資の向き先・内製化の兆候・**需要側の集中度** |
| Layer 4 提言の型 | 自社の**調達戦略**（深耕/複線化/共同開発/代替調達） | 自社の**供給戦略**（先回り開発/スイッチング防止/内製化への備え） |
| 提言の述語 | 「自社（買い手）は調達上〜すべき」 | 「自社（供給側）は先回りして〜すべき」 |

**垂直立場の例**（事実＝「対象企業のメモリ制御IPが特定少数に集中」）:
- `buyer` ✅「メモリ制御IPがキオクシア等少数に集中しており、一社依存の調達は供給・価格リスクが高い。自社（買い手）は複線調達か共同開発で交渉力を確保すべき」（供給集中 → 調達リスク）

#### 関係性立場（competitor / buyer / supplier）では「自社」を名指しして対象と対比する（`own_company` 指定時）

関係性立場の提言は「（競合として）参入余地がある」のような**主語の曖昧な一般論**に流れやすい。Phase A STOP-GATE C で自社名（`narrative_stance.own_company`）を確定した場合は、提言の主語を**自社の実名**にし、Web 調査で得た自社の事業・技術ポジションを対象企業（`subject_company`）と突き合わせて書く。「**誰にとっての**分析か」が具体化されて初めて実行可能な提言になる（buyer/supplier も同様に自社を名指しする。垂直版の例は上記）。

| ❌ NG（主語が曖昧な一般論） | ✅ OK（自社を名指しで対象企業と対比） |
|---|---|
| 「競合として、メモリシステム領域には参入の隙がある」 | 「キオクシアが手薄なAI向けストレージ制御は、NAND微細化に強みを持つサムスンにとって既存資産を活かせる参入好機である」 |

- 自社の強み/弱み/空白は **Web 調査で裏付け**、脚注（サイト名・URL・取得日）を付す（→ `data_notes.md` §3「自社（分析を行う側）の調査」）。自社は本母集団に十分現れないことが多く、Web が主な情報源になる。
- **集中度（HHI）を交渉力シグナルとして読む — 母集団が業界/技術ドメイン（タイプ A/A'/B）の時だけ**: 基本統計の出願人 HHI・上位集中度は、`buyer` 視点で「供給側の集中＝自社（買い手）の依存リスク・交渉力の弱さ」、`supplier` 視点で「需要側の集中＝自社（供給側）の交渉力の弱さ」のシグナルとして読める（Porter の買い手/売り手交渉力に対応）。⚠️ **対象が単一企業（タイプ C）の buyer/supplier 分析では出願人 HHI は無意味**（HHI≈1 で市場構造を表さない）＝算出せず、自社の依存・交渉力は Web 調査（対象企業の市場シェア・供給/顧客の集中・取引構造）から読む（→ `population_type_metrics.md`「タイプ C は出願人 HHI 算出無意味・そもそも算出しない」）。いずれにせよ**特許出願の集中 ≠ 市場・取引額の集中**なので断定せず、Web で裏付けて出所を付す。
- `own_company` が空（自社名を伏せる選択）の場合は、従来どおり主語を「（競合／買い手／供給側として）〜」とする一般的な関係性視点で書いてよい。
- `phase_d_gate.sh` Check 11s' が、関係性立場（`competitor` / `buyer` / `supplier`）かつ `own_company` 設定時に自社名がレポート本文へ登場するかを検査する（WARN）。
- **ミラーイメージング点検（関係性立場では必須・v9）**: 対象企業の合理性を**自社の理屈で測らない**。「自社から見て不合理な行動」を不合理と断定する前に、対象企業の置かれた文脈——**補助金／サプライチェーン／既存顧客／規制・認証／地域戦略／既存事業との接点**——の中では合理的な戦略でないかを点検し、**最低1点「自社から見ると不合理でも、対象から見ると合理的な戦略」を本文の一段落として書く**（置き場所は対象企業を論じる章・ミクロ分析B・提言章のいずれか）。例:「A社の低収益セグメントへの継続出願は、当社の採算基準では不合理に見える。しかしA社から見ると、同セグメントは主力製品の認証要件と共通する規格必須特許群であり、撤退はライセンス収入と交渉力の喪失を意味する——合理的な防衛である」。`phase_d_gate.sh` Check 32 が記述の有無を検査する（WARN。妥当性は判定しない＝人間が監査する）。詳細: `analysis/structured_techniques.md` §4。

→ 立場は **Phase B（洞察）・Phase C（deep_dive の So What）・Phase D（提言章・エグゼクティブサマリー）の分析の方向そのもの**を決める。Phase A で確定したら、呼称だけでなく**各章の解釈・提言のロジックを立場に合わせる**（`common_framework.md` の 4 層モデル、`deep_dive_guide.md` の Layer 4、`report_structure.md` の提言章でも同じ）。

> 立場が曖昧なまま `population_type = C`（単一企業）を理由に「当社」を採用するのが**最頻の誤り**。立場が未確認なら `neutral`（三人称）を既定とし、Phase A STOP-GATE C でユーザーに確認する。

### 6-3. 例外: 業界全体への一般化が許容される 2 条件

以下のいずれかを満たす場合に限り、**母集団外への一般化表現**（「業界では」「市場では」等）を使ってよい：

**条件 A: Web 調査・外部データでの裏付けあり**
- Web 調査で得た市場規模・業界統計・他社決算・政府統計などを `#footnote[...]` で引用した上で、その情報源に基づく一般化として書く
- 例: 「世界 CNF 市場は CAGR 17.5% で成長している#footnote[Grand View Research (URL), 取得日: 2026-04-14]」は許容（これは本母集団の観察ではなく外部データの引用）

**条件 B: 母集団が業界全体を十分カバーしていることが明示的に論証されている**
- `population_meta.query_intent` や `database_name` の設計から、母集団と業界全体のカバレッジがほぼ一致することが明示的に示されている場合（例: 業界団体が定義する全出願を網羅している等）
- この場合も初出時に「本母集団は業界の{概算カバレッジ}%をカバーしており、以降『業界』と『本母集団』を同義として扱う」等の定義を置くこと
- 定義なしに暗黙で同義化するのは禁止

**上記 2 条件に該当しない場合は、必ず「本母集団では〜」に限定表現すること。**

## 6.5 記述スタイル — 平易・正確（過剰修辞・気取った比喩の禁止・レポート/PPTX共通）

分析レポートは**事実と論理で説得する文書**であり、文芸的な比喩や扇情的な修辞は読者の判断を曇らせる。**平易・正確・具体**を旨とし、装飾的な言い回しを避ける（本ルールはレポート本文・別冊・PPTX すべてに適用）。

### 避けるべき表現（気取った比喩・大げさな修辞）
- ❌ 越境者 / 狼煙 / 地殻変動 / 試金石 / 旗手 / 号砲 / 幕開け / 夜明け / 胎動 / 風雲児 / 金字塔 / 羅針盤 / 苗床 / 三段ロケット / 主役交代 / 世代交代（語彙に対して）/ 〜の物語 等の比喩語
- ❌ 「〜は新たな夜明けを告げる」「地殻変動が起きている」「次代の旗手」のような扇情的な言い回し
- ❌ 体言止めの乱用・詩的な省略（読み手に解釈を委ねる曖昧表現）

### OK（平易・具体に言い換える）
- ✅ 「越境者」→「領域横断的な出願人」「複数分野にまたがる技術ブローカー」
- ✅ 「狼煙が上がった」→「出願が立ち上がり始めた」
- ✅ 「語彙の世代交代」→「主要語彙が基盤用語から応用用語へ入れ替わった」
- ✅ 「次の主戦場の号砲」→「次に競争が集中すると見られる領域」
- 比喩を使いたくなったら、**その比喩が指す事実・数値をそのまま書く**。

## 6.6 反復・水増しの禁止 — 行数は「量」でなく「固有性」で満たす（絶対遵守・レポート/別冊共通）

行数・件数の「最低◯◯」は**深さの目安であって、合否は内容の固有性で決まる**。文を繰り返して行数を稼ぐ「水増し」は、読者にとって無価値であり、機械ゲートで自動的に不合格になる。

### 禁止（＝`phase_d_gate.sh` Check 19 で FAIL）
- ❌ **同一文・同一構文の反復**: 同じ文を別の場所に何度も貼り付ける
- ❌ **回転名詞だけ変えた定型文の量産**: 「本母集団では〈X〉を単独の事実としてではなく…読む必要がある」の〈X〉だけを差し替えて並べる
- ❌ **連番定型見出しによる水増し**: 「○○観点 1」「○○観点 2」…「○○観点 34」のように、番号だけ変えた定型段落を量産する
- ❌ **特許リストへの定型1文スタンプ**: 代表特許を列挙して各件に「この特許は…の具体例である」のような同一文を貼るだけで、個別分析をしない
- ❌ **自明な一般論で字数を稼ぐ（反復でなくても水増し）**: データ（本母集団）を見なくても言える一般論を長々と書く。例:「特許は権利文書である」「定型語は技術的意味を持たない」「あらゆる請求項に共通語が出現する」「学術は技術概念で語り特許は権利範囲を画定する」。これらは本母集団の固有性を一つも語っていない。**各段落は本母集団固有の事実（固有の数値・公開番号・クラスタ名・出願人名のいずれか）を最低1つ含めること**。字数不足は一般論ではなく**固有の事実**（新しい代表特許・数値根拠・別クロスパターン・Web裏付け）で埋める。
  - ❌ NG（自明な一般論で字数稼ぎ）: 「定型語は技術的意味を持たないが、あらゆる請求項に共通して出現するため高い共起頻度を示す。特許は権利文書であり、学術が技術概念で語るのとは性格が異なる…」
  - ✅ OK（本母集団固有の数値と解釈）: 「技術的に意味のある語の中心性上位は『樹脂組成物』（中心性0.93・頻度591）『添加剤』（0.87・320）…で、本母集団の技術的骨格が応用製品ではなく素材設計にあることを示す。急成長語『化粧シート』がネットワークの周辺に位置する点は、応用の多様性と素材基盤の共通性という中心-周辺構造を表す。」

### OK（固有の事実で埋める）
- ✅ 行数が足りない時は、文を繰り返す代わりに **①新しい代表特許（固有の公開番号）②新しい数値根拠 ③別のクロスパターン ④Web調査の裏付け** を足す
- ✅ **各段落は前段落と異なる固有の事実を最低1つ含める**（その段落でしか言えないことを書く）
- ✅ 代表特許は1件ごとに固有の事実（出願年・IPC・出願人・その特許固有の技術的特徴）に触れる

### 自動チェック
`phase_d_gate.sh` の **Check 19（反復・水増し検出）** が、正規化した本文で①同一文の反復回数 ②回転名詞テンプレの量産 ③重複文比率 ④連番定型見出し数 を機械的に測り、閾値超で **FAIL** にする（report.typ・report_executive.typ 両方）。
